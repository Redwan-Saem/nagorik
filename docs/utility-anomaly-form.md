# Utility anomaly form (T-009.7)

Residents can open /reports/utility-anomalies/create from the navigation or the general report form. The MVC action verifies the authenticated resident and loads the current area lookup. The existing generic report form remains available. No database migration is needed.

The form submits multipart data with same-origin authentication to the T-009.4 POST endpoint. It provides all six anomaly types, area, address/landmark, a 10–1000 character description with counter, one to three photo previews and optional GPS. JPG/PNG extension, MIME, signature and 5 MiB limits are checked before submission; server validation remains authoritative. Object URLs are revoked when selections change, photos are removed or the page is left. Stale asynchronous photo checks cannot overwrite newer selections.

GPS is requested only when the resident clicks its button. Denial, unavailability and thrown browser errors retain the address-only path. A pending lookup can be cancelled with Use address only, and late callbacks are ignored. Coordinates never replace the required address. Form submission waits while GPS is pending and disables input/submission during the POST to prevent duplicate clicks.

The high-risk type list is generated by UtilityAnomalyRules rather than a second client-side risk mapping. Its warning advises keeping distance and not approaching for photos or attempting repair, and links to the existing SOS request page.

Validation errors appear beside labeled fields with aria-invalid and described-by associations. Status and error messages use live regions; client validation focuses the first invalid field after re-enabling it. Previews and long filenames fit narrow screens. User-provided filenames and server messages use textContent.

On HTTP 201, the client validates the returned ID/reference and redirects to the existing owner-restricted /Reports/Confirmation/{id} page. That page now displays the utility UA reference and persists the duplicate warning through the redirect. The following T-009.8 task can extend the confirmation and My Reports UI further.

HTTP 429 preserves input, displays retry guidance and disables submission for Retry-After, without automatic resubmission. HTTP 400 maps field errors; 401 offers sign-in, 403 explains resident-only access, and 413 explains photo limits. Network failures, malformed success or server errors offer My Reports so the resident can check whether submission succeeded before explicitly retrying. Existing input is retained.

Verification: 25 client tests cover multipart payloads, pending duplicate clicks, field/description/photo validation, previews and cleanup, safe text insertion, stale photo checks, all high-risk types, GPS fallback/cancellation, duplicate warnings, cooldown expiry and API/network errors. HTTP tests cover page authorization, encoded database area names, accessibility hooks, navigation and owner-only confirmation with reference/duplicate feedback. Desktop and 390-pixel layout checks used a locally served snapshot rendered by the MVC test host with the actual CSS/JavaScript; API success/failure behavior was checked separately through HTTP integration tests.
